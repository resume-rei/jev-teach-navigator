# Jev 契約の再確認と画像経路の境界

確認日: 2026-10-18。公開の公式資料を閲覧し、ローカルの合成データと模擬応答で契約を検証した。実 API、課金推論、実画面の外部送信は行っていない。

## 公式資料と今回の反映

| 項目 | 公式の契約 | この実装 |
| --- | --- | --- |
| [Choice](https://docs.typesafe.ai/primitives/choice) | 最大255選択肢。回答に選択肢、全候補の確率分布、confidence。質問は同じ state に対して並列に評価される | 候補254件と none。候補IDの重複・予約語衝突を拒否し、回答型・既知ID・確率分布を検査する |
| [Noul](https://docs.typesafe.ai/primitives/noul) | `type: noul` と `noul`。数値は yes の確率であり、程度や独自 confidence ではない | スキル適合・対象の存在は型と0〜1の値を検査する |
| [Box](https://docs.typesafe.ai/primitives/box) | 1質問につき説明した1対象の矩形。四辺は画像に対する0〜1の比率。対象不在でも矩形が返る | 存在確認が低いときは矩形を捨てる。辺の順序・有限値・寸法を検査する |
| 同名・複数対象 | Box資料は区別できない場合に none / one / several のChoiceを併設する方法を示す | `present`、`matches`、`target`を同じ既知の対象へ独立に質問する。one と存在の両方を確認できたときだけ矩形を採用する |
| モデル | Box資料は `jev-preview` または `jev-1.14.0` を指定する | 既存の固定値 `jev-1.14.0` を維持。モデルが実際に利用可能か、アカウントに権限があるかは未確認 |
| [Images](https://docs.typesafe.ai/images) | 画像またはBox質問には `TypeSafe-Danger-Zone-Images: true` が必要 | 送る本文からヘッダーの要否を決める。呼出元のフラグ指定漏れに依存しない |
| 画像の寸法 | **各辺280〜1568px**、総画素78,400〜2,458,624 | 旧実装が許容していた256×400px等を拒否する。280×280pxと最大辺の境界を合成画像で確認した |
| 画像の容量 | PNG/JPEGの静止画像、1画像16MiB、request・processed images・expanded requestは各32MiB | 1枚に限定し、ファイル容量とJSON送信量を検査する。API内の再エンコード後の容量はローカルで保証できないため、API拒否時は停止する |
| 画像参照 | 各画像参照の使用ごとに展開量が増える。UUID参照が推奨される | UUIDをstateに1回置き、質問からstateのフィールドを参照する。撮影・縮小・crop・再送を自動で行わない |

公式資料は画像とBoxを試作向けと位置付け、仕様・精度が変わり得るとしている。0.9等の判定閾値はこのプロジェクトの保守的な仮値であり、公式推奨値でも実測済み精度でもない。

## 選択・位置特定・生成を分ける

対象の意味が既に決まっていれば、同じ画像に対して存在・個数・Boxを1リクエストで質問できる。この3問は、他の質問の回答を読み取らない。

Choiceで初めて選ばれる対象のBoxは、Choice回答をローカルで検査してから作る別リクエストとする。前の呼出で使った送信承認を流用できない。候補選択そのものと、選択後の現在位置の発見を同一の処理として扱わない。

`buildGenerationRequest` / `applyGeneration` は教示説明を整理する別のアダプターで、観察済みの操作・パラメータ・完了証拠を生成結果で置き換えない。`buildDraftRequest` / `parseDraft` の入力案にも操作権限はない。採用する場合は全文を提示し、入力と送信を別々の承認へ結び付ける。

## 修正した契約・実装上の問題

- `OneCallPermit`の承認・使用状態を非公開にし、承認済みのJSON本文をそのまま1回だけ送る。以前の複数回serializeでは、状態を持つ`toJSON`が承認照合後に別の内容を返せた。タイムアウト、不正JSON、HTTPエラーでも送信承認は消費される。
- API応答のJSON解析失敗は固定メッセージに変換し、解析例外に含まれ得るレスポンス断片を表示しない。
- Boxの入力画像から読んだ寸法と、位置変換用の寸法を送信前に照合する。応答待ちの間に呼出元が引数を書き換えても、別の対象・cropへの変換には使わない。
- 画像・cropのゼロ、負の寸法、NaN、Infinity、加算overflowを拒否する。複数モニターの負の原点は許容する。この純粋関数テストはDPIや複数モニターの実機試験ではない。
- PNGのCRC、画像データの存在、切断、アニメーション、終端後のデータと、JPEGのsegment境界・画像データ・終端を検査する。これはコンテナの事前検査であり、完全な画像デコーダーや画像内容の正しさの保証ではない。画像のmetadataやEXIF orientationの取り扱いは送信前の準備と確認が必要で、APIの自動回転を仮定しない。

従来の`present`と`target`だけの模擬応答は、一意性の証拠がないため新しい`JevProvider.locate`では採用しない。実API検証を行う場合も、必ず新しい`buildBoxRequest`で送信内容を作り直す。

## Windowsへの接続境界

この変更は、WindowsのUIA案内から画像APIを自動で呼び出す機能ではない。UIAで現在対象を一意に取得できる場合はUIAを使い、取得できない対象は保留する。Jevアダプターが返した矩形だけで、Windows側のクリック権限を作ってはならない。

画像経路を実機に接続する次の段階では、利用者が送信画像・対象・接続先・モデル・課金を確認する。その後も画像取得時点、対象ウィンドウの登録、座標変換、提案IDと有効期限を同じ観察へ結び付け、Enter後の実行直前に再観察する必要がある。前の画像で得た矩形を次の操作へ再利用せず、実行結果が不明なら再実行しない。
